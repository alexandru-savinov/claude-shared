Define three reusable Claude Code agent types — `forge`, `reader`, `adversary` — as `content/agents/*.md` files, so the delegation rules Alexandru currently has to retype into every task prompt live in the agent's own frontmatter and system prompt instead.

## Context

Today `content/agents/` holds one file, `nix-security-reviewer.md`. It has a proven shape: YAML frontmatter (`name`, `description`, `tools`, `model`) followed by a markdown system prompt, `tools:` on a single line, using scoped `Bash(<cmd>:*)` prefixes rather than a bare `Bash`. Per `README.md`, files under `content/agents/` are symlinked live into `~/.claude/agents` by the home-manager module and become dispatchable after `nix flake update claude-shared` + a host rebuild — this plan only authors the files; deployment and any first live dispatch happen after merge, outside this plan's scope.

Three real incidents motivate the three types, and each type's file should make the corresponding failure as hard to reach as this deployment actually allows — see the enforcement finding below for what that ceiling really is:

1. **2026-08-19** — an agent holding raw public-comment capability (`gh pr comment`) plus a "report findings on the PR" mandate posted the mechanism of an unpatched CRITICAL vulnerability onto a public PR.
2. **Triage-tool mishap** — a recon/audit pass probing a CLI's `--help` output caused a write into `sidequests.jsonl` (the `--help` text got captured as a quest).
3. **Adversary check that couldn't fail** — a freshly built regression check passed green while the exact bug it existed to catch was live, twice. An adversary agent's job is specifically to break things and report what did and didn't break, including negative results.

**Baseline before this plan starts:** `main` is green — `git status` clean, no open conflicting PRs touching `content/agents/`. Confirmed in Task 0.

**Capability-gate enforcement — tested empirically, 2026-08-20, not assumed.** Before writing the three files, this plan's author dispatched the ALREADY-DEPLOYED `nix-security-reviewer` agent (tools: `Read, Grep, Glob, Bash(systemctl:*), Bash(tailscale:*), Bash(nix eval:*)` — no `Write`/`Edit`) and asked it to (a) write a file and (b) run a Bash command outside its declared prefixes. Result: it wrote the file anyway via `Bash` with `echo ... > file` (no Write tool needed — Bash sufficed), and it ran `git log -1`, a command matching none of its three declared prefixes, with no refusal or error. `module/default.nix`'s `baseSettings` sets `permissions.defaultMode = "auto"` and `skipDangerousModePermissionPrompt/skipAutoPermissionPrompt = true` fleet-wide — which explains it: the `Bash(<cmd>:*)` prefixes are a permission-*approval* matcher (what would need confirmation, absent auto-mode), not a per-invocation sandbox on the Bash tool itself. Once any `Bash(...)` entry makes the Bash tool available to an agent at all, that agent can run arbitrary shell in this deployment, including writes, regardless of how narrowly the prefixes were scoped. This establishes the negative claim — scoped Bash leaks — for an agent that HOLDS Bash; it says nothing about, and this plan does not claim it tested, an agent holding no Bash tool at all (see `reader` below).

This changes the design:

- **The only VERIFIED write-safe configuration is granting no Bash tool at all.** `Read`, `Grep`, `Glob` are first-class, non-shell tools (not wrappers around a shell), so they carry no equivalent escape observed or plausible here — but this plan has not itself dispatched a Bash-less agent to confirm it, and says so explicitly rather than overclaiming (see Task 4's held-for-human follow-up).
- **`forge` and `adversary` cannot avoid Bash** — committing/pushing/opening a PR, or running a test suite to try to break something, requires a shell. For these two, the `tools:` line and the exclusion of `gh pr comment` / `gh pr edit` / `gh api` / write-tools (for `adversary`) are declared-intent and behavior-steering — they reduce what the model reaches for and would matter the moment this fleet's permission mode stops being blanket-`auto` — but they are **not**, today, a hard technical boundary. This plan states that plainly in each file's own system prompt (Tasks 1 and 3) rather than implying a guarantee the fleet doesn't back.
- **`reader` gets built around this finding**: no Bash entries at all, only `Read, Grep, Glob`. This sacrifices shell-based recon (`git log`, `gh pr view` as commands) in exchange for the property this plan can mechanically prove at rest (no Bash token on its tools line) and reasonably expects — but has not itself observed — to hold at dispatch time, because there is no Bash tool to escape through.

This is a materially different (smaller, more honest) claim than a first draft of this plan made before the probe ran. If a future editor is tempted to re-add scoped Bash prefixes to `reader` for recon convenience: don't — it was tested on a comparable agent and did not hold.

**Live-dispatch follow-up — held for a human, not part of this plan's closing check.** Dispatching a real subagent from inside a headless ralphex task session requires the agent type to already be deployed (symlinked into `~/.claude/agents` via the home-manager module + a host rebuild), which is outside this plan's scope. After merge + deploy, a human (Alexandru, or an agent he directs) should: dispatch `reader` once against `content/agents/fixtures/reader-refusal-fixture.md` and confirm by observation that it refuses/cannot comply (expected: clean, since it has no escape hatch — this would be the first real test of the claim above); dispatch `forge` once and confirm it can `gh pr create` and does not attempt `gh pr comment`; dispatch `adversary` once and confirm its report includes at least one tried-and-failed probe, not only successes. Task 4 verifies this paragraph is still present, not that the dispatches happened.

**Verification-command hygiene, learned from an external review of this plan's first draft (revmux, 2026-08-20):** an earlier version of Tasks 1–3 checked forbidden/required strings against the ENTIRE file rather than just the `tools:` line. That let legitimate system-prompt prose (e.g. the sentence forbidding `gh pr comment`) trip a whole-file forbidden-string grep, and let a trailing bare `Bash` or an injected `Write` slip past an anchored `^\s*(...)\b` pattern that only matches at the very start of a line (the `tools:` line begins with the literal word `tools:`, not with a capability name). The negative arms in that draft also injected one string and grepped for that same string, proving only that `sed`/`grep` run — not that the real positive check reacts to the mutation. Every check below is corrected to (a) extract the `tools:` line first, then grep only that, and (b) have each negative arm re-run the exact positive-check command against the mutated copy and require the count to flip from 0 to ≥1.

- `reader` holds `Read, Grep, Glob` and nothing else — zero Bash entries, scoped or not. This is the one property this plan can mechanically prove holds at rest (grep for the absence of the string `Bash` on its tools line) and reasonably expects, but has not itself observed, to hold at dispatch time.

Both facts are checked at rest (grep, scoped to the `tools:` line) but are NOT proven to hold at dispatch time under this fleet's `permissions.defaultMode: auto` — say so in both files, don't imply a sandbox that was tested and found absent.

- Every checklist item whose check gates a WRITTEN ARTIFACT against forbidden content (Tasks 1, 2, 3, and Task 4's frontmatter-match loop) must include a negative arm that re-runs the exact same positive-check command against a deliberately mutated copy and shows the count flip. - Every `tools:`-line check in this plan operates on the single line matched by `grep '^tools:'`, never on the whole file — system-prompt prose is free to name forbidden commands for clarity without tripping a forbidden-string check meant for the capability declaration.
